# ADR-001 — Adaptive Worksheet Engine with OMR Scan Loop

**Status:** Proposed  
**Date:** 2026-06-04  
**Author:** Research Agent Synthesis  
**Related:** `docs/research/research-report-001-dr-math-adaptive-engine.md`, `docs/decisions/DECISION-20260614-001-pdf-rendering.md`, `docs/decisions/DECISION-20260615-002-pdf-observability-concurrency.md`

---

## Context

We have a working foundation in OpenMAIC:

- Student roster with CRUD and CSV/Excel import.
- Single and batch worksheet PDF generation using LLMs + Playwright.
- Server-side PDF rendering with concurrency limits and structured JSON logging.
- Vision-LLM OCR marksheet scanning (proof-of-concept).

The next strategic leap is the user’s **“Dr. Math”** vision: a continuous adaptive loop where each student’s performance updates a multi-dimensional **Mark**, and the next worksheet is selected to match that Mark. The loop must work in low-resource Indian schools and tuition centers, which means it must support **printed worksheets + phone-camera OMR scanning** in addition to any digital practice mode.

This ADR records the research-backed decision on architecture, algorithms, and go-to-market.

---

## Decision

We will build a **hybrid adaptive worksheet engine** with the following properties:

1. **Student state = Mark.** A per-student, per-topic multi-dimensional vector combining accuracy, response time, hint usage, error type, IRT ability θ, BKT mastery probability, and known gaps.
2. **Adaptive selection = 1PL IRT + BKT.** 1PL IRT drives real-time next-question selection; BKT drives explicit skill-mastery reporting.
3. **Offline input = printed worksheet + OMR scan.** Phone-camera capture of a corner-marker OMR sheet, processed server-side by a Python/OpenCV microservice.
4. **Online input = `/practice` digital question stream.** Records the same response events directly.
5. **Output = next worksheet PDF.** Generated by the existing LLM + Playwright pipeline, seeded with Mark-aware prompt context.
6. **Beachhead market = tuition centers + one anchor private school.** Schools provide credibility; tuition centers provide faster feedback loops.

### Why this combination?

- **No incumbent owns the closed loop** of AI worksheet → print → OMR scan → adaptive next worksheet in India [R1–R9].
- **Server-side OMR** gives the highest accuracy and fastest iteration at MVP stage versus on-device or commercial SDKs [R10–R14].
- **1PL IRT** is the simplest research-backed continuous-ability model; **BKT** adds interpretable skill mastery without overcomplicating the selection loop [T5, T6].
- **Tuition-center-first GTM** avoids the 4–9 month school sales cycle while generating outcome proof [G1].

---

## Consequences

### Positive

- Differentiated product: worksheet + OMR + adaptive loop is not offered as a tight, affordable SaaS by major Indian ed-tech players.
- Interpretable diagnostics: IRT θ and BKT P(mastery) give teachers concrete numbers.
- Extensible: the same Mark engine can later power digital practice, chat tutoring, or parent dashboards.
- Low client-side hardware requirements: OMR heavy lifting happens on the server.

### Negative / Trade-offs

- Adds a new runtime (Python/FastAPI) for OMR; increases deployment surface.
- Requires a calibrated question bank before IRT is fully effective; early deployments rely on expert-tagged difficulties.
- OMR accuracy depends on print quality and capture guidance; needs manual-review fallback.
- School sales still require principal-level engagement; tuition-center success is necessary before large school rollout.

---

## Alternatives Considered

| Alternative | Why rejected |
|-------------|--------------|
| Pure DKT neural model for selection | Higher predictive accuracy but low interpretability; needs large response dataset not yet available [T8]. |
| On-device OMR only | Slower iteration, lower accuracy on low-end phones, harder cross-platform deployment [R10]. |
| Digital-only adaptive practice | Ignores the paper-worksheet reality of most Indian schools and tuition centers. |
| Sell directly to large school chains first | Sales cycle 6–12+ months; too slow for MVP validation [G1]. |

## Implementation Sketch

```
┌──────────────────────────────────────────────────────────────┐
│  INPUTS                                                      │
│  • Digital /practice response (Next.js → API)                │
│  • OMR scan image (phone camera → /api/omr/grade)            │
└──────────────────────┬───────────────────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────────────────┐
│  MARK SERVICE                                                │
│  • Update accuracy streak, response time, hints, error type  │
│  • Re-estimate IRT θ (MLE / EAP)                             │
│  • Update BKT P(mastery) per skill                           │
│  • Emit PII-free telemetry                                   │
└──────────────────────┬───────────────────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────────────────┐
│  SELECTOR SERVICE                                            │
│  • Score candidates: info(θ,b) + skill gap + misconception   │
│  • Enforce exposure limits, spaced repetition, prerequisite  │
│  • Return ordered question list for next worksheet           │
└──────────────────────┬───────────────────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────────────────┐
│  OUTPUT                                                      │
│  • LLM-generated worksheet PDF (existing pipeline)           │
│  • OMR-gradable bubble sheet appended                        │
│  • Teacher/parent diagnostic digest                          │
└──────────────────────────────────────────────────────────────┘
```

### Services

| Service | Tech | Responsibility |
|---------|------|----------------|
| Web app | Next.js (existing) | UI, roster, worksheet preview, practice mode, scan capture. |
| Worksheet API | Next.js API routes (existing) | LLM question generation, PDF rendering. |
| OMR service | Python/FastAPI + OpenCV + OMRChecker-style pipeline | Image → answers + confidence + annotated image. |
| Mark service | TypeScript (can live in Next.js API) | State updates, IRT/BKT calculations. |
| Selector service | TypeScript | Question scoring and worksheet assembly. |
| Object store | MinIO / S3 | Scanned images, annotated outputs, PDF archives. |
| Database | PostgreSQL | Students, marks, question bank, response logs. |

---

## Metrics for Success

| Metric | Target | Measurement |
|--------|--------|-------------|
| OMR grading accuracy | ≥ 95% on clean scans, ≥ 90% on phone captures | Hold-out test set of 200 sheets |
| Next-question prediction (AUC) | ≥ 0.70 | Held-out student responses |
| Teacher worksheet creation time | ≤ 2 min vs. 20 min manual | Time-to-PDF in pilot |
| Tuition center pilot retention | ≥ 70% after 8 weeks | Active weekly usage |
| Student response events logged | ≥ 1,000 per topic | Within first pilot term |
