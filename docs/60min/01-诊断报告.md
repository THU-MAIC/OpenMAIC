# OpenMAIC 60 分钟长课改造 · 诊断报告

> 审计基线：`fe2cf7d`（2026-10-30，v1.3.0 版本线）
> 审计范围：大纲生成 → 场景内容 → 讲解动作 → 旁白合成 → 视频导出 全链路
> 结论：**当前架构是按 15-20 分钟短课设计的，60 分钟不是"把页数乘以四"，而是四个结构性约束同时失效。**

---

## 一、结论摘要

| # | 缺口 | 一句话 |
| --- | --- | --- |
| 1 | 时长是"猜"出来的，不是"算"出来的 | 时长只存在于用户自由文本里，模型自己推断，且默认 15-20 分钟；`estimatedDuration` 字段全链路只透传、无消费方 |
| 2 | 场景密度默认是短课节奏 | 硬编码"1-2 场景/分钟"→ 60 分钟等于 60-120 页，正好撞上原 `MAX_OUTLINE_SCENES = 100` 上限 |
| 3 | 没有"模块"这一层 | 课程是扁平场景列表，无单元/章节/教学功能划分，60 分钟的内容无法形成论证弧线 |
| 4 | 跨页记忆只有 1 页 | `previousSpeechesFor()` 只回传**上一页**的讲稿，第 20 页不知道第 5 页讲过什么 |
| 5 | 生成与渲染成本随页数线性爆炸 | 默认串行生成（`PARALLEL_SCENE_CONCURRENCY` 未设即为 0）；渲染服务自述"10 分钟视频需要数十分钟" |

## 二、现状基线（代码证据）

### 2.1 大纲阶段把课程当成"一节课的页列表"

`packages/@openmaic/generation/templates/requirements-to-outlines/system.md`：

```
| Course Duration     | 15-20 minutes          |     ← 默认时长
- **Duration Control**: Each scene should be 1-3 minutes   ← 每页 1-3 分钟
8. Arrange scenes by inferred duration (typically 1-2 scenes per minute)
```

- 没有任何结构化时长字段：`UserRequirements`（`lib/types/generation.ts:93`）只有 `requirement: string`，注释明写"All details (topic, duration, style, etc.) should be included in the requirement text"。
- `estimatedDuration`（`lib/types/generation.ts:150`）在 schema 里被读取（`outline-schema.ts:187`）、被透传（`packages/@openmaic/generation/src/outline-type.ts:28`），**但没有任何地方用它做校验、配平或提示**。也就是说：模型写"这一页 3 分钟"和写"这一页 30 秒"，对系统完全等价。

**后果**：60 分钟的课，页数由模型即兴决定。实测两种失败形态稳定复现——
- 形态 A：模型按 1-2 页/分钟给 60-100 页 → 每页 30-60 秒讲完 → 变成"幻灯片朗读竞速"；
- 形态 B：模型给 12-15 页 → 每页要撑 4-5 分钟 → 单页旁白必然空洞或超时。

### 2.2 硬上限与成本上限刚好卡在 60 分钟附近

- `lib/server/generation/outline-schema.ts:20`：`MAX_OUTLINE_SCENES = 100`（本次已提升至 240）。
- `lib/server/generation/steps/outline.ts`：`MAX_OUTLINE_STREAM_BYTES = 512 * 1024`，一次性流式读取单次模型输出的完整 JSON。
- 也就是说，60 分钟的"形态 A"（60-100 页）刚好贴着上限跑，而单次调用输出 60-100 个带 keyPoints 的场景对象，本身就在逼近模型的稳定输出区间——越靠后的场景质量越容易塌。

### 2.3 没有模块层，课程是一条直线

`lib/server/generation/run/plan.ts` 的步骤计划是：

```
material-analysis → research → outline → [确认] → agents
→ scene:0:content → scene:0:actions → scene:0:narration
→ scene:1:content → ...
```

`SceneOutline`（`lib/types/generation.ts:141`）的字段是 `title / description / keyPoints / teachingObjective / estimatedDuration / order`——**没有 module / unit / section / 教学功能 任何一层**。

**后果**：60 分钟的课没有"这一段在干什么"的显式契约。哪几页负责建立概念、哪几页负责推导、哪几页负责迁移，全靠模型在生成第 3 页时自觉，而第 3 页看不到第 30 页。

### 2.4 跨页连贯性的窗口只有 1 页

`lib/server/generation/run/engine.ts:776`：

```ts
const previousSpeechesFor = (index: number): string[] => {
  for (let before = index - 1; before >= 0; before -= 1) {
    ...
    if (actions) return actions.previousSpeeches ?? [];   // ← 命中最近一页即返回
  }
  return [];
};
```

`SceneGenerationContext.previousSpeeches` 的注释也写着 "Speech texts from the previous page only"。

**后果**：这是 60 分钟最致命的一条。短课里"上一页讲了什么"够用；长课里第 20 页需要知道第 5 页立了什么约定、第 12 页埋了什么伏笔，而它拿不到。表现为三种固定症状：
- 第 3 页开始重新自我介绍；
- 第 19 页把第 4 页的定义再讲一遍；
- 第 12 页就开始做全课总结。

现有的 `slide-actions/system.md` 用一段文字约束来打补丁（"This is NOT a series of separate classes"、"First page / Middle pages / Last page"），但约束的是**语气**，不是**内容记忆**。

### 2.5 生成与渲染成本

| 环节 | 现状 | 60 分钟量级 |
| --- | --- | --- |
| 场景生成 | 每页 3 次模型调用（content / actions / narration），默认串行（`lib/server/provider-config.ts:1093`，未设 `PARALLEL_SCENE_CONCURRENCY` 即返回 0） | 27 页 = 81 次调用；按每次 20-40s 串行，**27-54 分钟** |
| TTS | 每页按段合成，有长度切分（`lib/audio/tts-utils.ts`） | 约 12,000 字中文旁白 |
| 视频导出 | `render-service/README.md` 自述 "a 10-minute video can take tens of minutes" | 60 分钟 ≈ **数小时**，且单 job 超时/资源策略需重估 |

并行开关存在（`PARALLEL_SCENE_CONCURRENCY`，上限 10），但默认关闭，且并行模式下 content 失败的处理路径不同（`engine.ts` 注释提到"browser marks a scene whose content failed"）。

### 2.6 稀缺资源限制是按短课写的

`requirements-to-outlines/system.md`：

```
- Limit to 1-2 interactive scenes per course
- Limit to at most 1 PBL scene per course
```

`slide-actions/system.md`：

```
- FREQUENCY: Do NOT add a discussion to every page. ... A typical course should have at most 1-2 discussions total.
```

对 15 分钟课合理；对 60 分钟课，**一节课只有 1 次互动 = 每 60 分钟只有 1 个注意力锚点**，这直接违反长课的基本节奏要求（见 `02-60分钟长课架构.md` 第 2 节）。
