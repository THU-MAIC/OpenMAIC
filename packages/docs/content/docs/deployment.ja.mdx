OpenMAIC は Next.js アプリケーションで、常駐する Node.js プロセスと PostgreSQL が必要です。授業の生成はサーバー側で行われます。各生成はデータベースに記録され、サーバープロセス内のワーカーが実行します。ブラウザがページを離れても生成は続き、プロセスが停止した場合は別のプロセス（または再起動した同じプロセス）が最後に完了したステップから引き継ぎます。サポートするデプロイ方法は次の 2 つです。

- **Docker Compose**（推奨）：アプリと PostgreSQL の 2 つのコンテナ。
- **Docker イメージまたは `pnpm start`**：自分で運用する PostgreSQL と組み合わせます。

1.2.0 以降、Vercel などのサーバーレス環境はサポートしません。リクエストとともに終了する関数では生成を実行できないためです。下記の「Vercel（1.1.x まで）」を参照してください。

## Docker

リポジトリには本番向けの `Dockerfile` が含まれています。イメージは Node.js 22 を使用しています。ビルドして実行します：

```bash
docker build -t openmaic .

docker run --env-file .env.local -e DATABASE_URL=postgres://user:password@db-host:5432/openmaic -v openmaic-data:/app/data -p 3000:3000 openmaic
```

リポジトリにある Docker Compose 設定の利用を推奨します：

```bash
cp .env.example .env.local
# .env.local（キーとサーバーオプション）を編集してから：
docker compose up --build
```

デフォルトの Compose デプロイは OpenMAIC アプリと PostgreSQL の 2 つのコンテナを起動し、両者の間の `DATABASE_URL` を設定して、`openmaic-data` と `openmaic-postgres` ボリュームをマウントします。その他のプロバイダーや機能は必要に応じて設定してください。詳細は[設定説明](./configuration.mdx)を参照してください。

モデルの設定方法は 2 通りあります。個人利用のインストールでは、スタックを起動してアプリを開き、モデル設定でモデルサービスを接続します。設定はデータベースに保存されます。ファイルで管理するデプロイでは、`openmaic.example.yml` を `openmaic.yml` にコピーし、キーを `.env.local` に置いてファイルをマウントします（後述）。[設定説明](./configuration.mdx#モデルとプロバイダー)を参照してください。

イメージはボリュームのデータディレクトリを実行ユーザーの所有で作成するため、新しいボリュームではそのまま授業と利用記録が保存されます。古いイメージが作成したボリュームは root 所有の場合があり、その場合アプリは通常どおり動作しているのに、サーバー側の保存がすべて `EACCES` で失敗します（授業は気づかれないままディスクに書き込まれず、ログに `Failed to record usage ... EACCES: permission denied` が出ます）。このようなボリュームは一度修復してから、アプリを再起動してください。

```bash
docker exec -u root <container> chown -R 1001:1001 /app/data
```

`NEXT_PUBLIC_*` の機能フラグは Docker ビルド時に注入されるため、実行時の `.env.local` に書くだけでは反映されません。例えば動画エクスポートと実験的な PPTX インポートを有効にする場合：

```bash
NEXT_PUBLIC_ENABLE_VIDEO_EXPORT=true \
NEXT_PUBLIC_ENABLE_PPTX_IMPORT=true \
docker compose --profile video-export up --build
```

他のクライアント機能フラグも同様に渡せます。`docker build` を使う場合は対応する `--build-arg` を利用してください。

`openmaic.yml` を使うには、アプリの作業ディレクトリにマウントするか、別の場所にマウントして `OPENMAIC_CONFIG` でそのパスを指定します。

```yaml
services:
  openmaic:
    volumes:
      - ./openmaic.yml:/app/openmaic.yml:ro
```

ホストに存在しないパスはマウントしないでください。Docker がその場所にディレクトリを作成し、サーバーが起動を拒否します。`docker run` では `-v "$PWD/openmaic.yml:/app/openmaic.yml:ro"` を追加します。ファイルを編集したらコンテナを再起動してください。`openmaic.yml` は `.dockerignore` に含まれているため、リポジトリからビルドしたイメージに焼き込まれることはありません。実行時にマウントしてください。`openmaic.yml` がない場合は、旧来の `server-providers.yml` が引き続き `/app/server-providers.yml` から読み込まれます。

Docker コンテナ内の `localhost` はコンテナ自身を指します。ホスト上で Ollama、Lemonade、VoxCPM、ComfyUI を動かしている場合は、`http://host.docker.internal:11434/v1` や `http://host.docker.internal:8188` のように `host.docker.internal` を使ってください。Linux の Docker では通常、`openmaic` サービスに `extra_hosts: ["host.docker.internal:host-gateway"]` も必要です。`openmaic.yml`（または旧来の変数）で宣言したプロバイダーはサーバー管理なので、そのエンドポイントは `ALLOW_LOCAL_NETWORKS` なしでホストやプライベートネットワーク上に置けます。この変数が関係するのはユーザーが入力するエンドポイント、つまり **設定 → モデル** で追加したチャットの Base URL と、非推奨のリクエストフィールドだけです。

## 自前の仮想マシンでのセルフホスト

ホストには Node.js `22.19.0` 以上と pnpm `10.28.0` が必要です。`pnpm` でビルドして起動します：

```bash
pnpm install
pnpm build
DATABASE_URL=postgres://user:password@db-host:5432/openmaic pnpm start      # デフォルトでポート 3000 をリッスンします
```

プロセスマネージャー（systemd、pm2、コンテナなど）で常時稼働させ、停止時に再起動されるようにしてください。TLS 終端は nginx や Caddy などを前段に置いてください。授業と生成された授業メディアは PostgreSQL（または S3）に保存されるため、データディレクトリと同じ `OPENMAIC_SECRET_KEY` もあわせて共有すれば、複数のインスタンスで 1 つのデータベースを共有できます（下記参照）。

## 必須の設定

| 設定 | Docker Compose | Docker イメージまたは `pnpm start` |
| --- | --- | --- |
| `DATABASE_URL` | 同梱の PostgreSQL を指すよう設定済み | 必須。未設定ならサーバーは起動時に終了します |
| ID モード | シングルユーザー（`docker-compose.defaults.env` の `OWNER_SINGLE_USER=true`） | 未設定ならブラウザごとに匿名オーナーになります |
| `OPENMAIC_SECRET_KEY` | 任意。生成されたシークレットは `openmaic-data` ボリュームに保存されます | 複数インスタンスの場合、または永続的な `data/` ディレクトリがない場合は必須 |
| データディレクトリ | `/app/data` にマウントした `openmaic-data` ボリューム | 作業ディレクトリの永続的な `data/` ディレクトリ。すべてのインスタンスで共有 |
| モデル | `openmaic.yml` または **設定 → モデル** | 同左 |

**ID モード**は授業の所有者を決めます。未設定の場合、ブラウザごとに別々の匿名オーナーとなり、別のブラウザでは空のライブラリが表示されます。個人利用では `OWNER_SINGLE_USER=true`、1 つのチームで 1 つのライブラリを共有する場合は `ACCESS_CODE` とあわせて `PERSISTENCE_SHARED_OWNER_ID` を設定し、実際のアカウントが必要な場合はオーナー認証メソッドを登録してください。詳しくは README の [Owner identity](https://github.com/THU-MAIC/OpenMAIC#owner-identity) と `.env.example` を参照してください。

**`OPENMAIC_SECRET_KEY`** はモデル設定に保存されたプロバイダーキーを暗号化します。未設定の場合、各インスタンスが `data/instance-secret.key` に独自のシークレットを作成するため、データベースを共有するインスタンス同士で保存済みキーを読み取れません。データベースのバックアップと一緒に保管してください。[シークレットと OPENMAIC_SECRET_KEY](./configuration.mdx#シークレットと-openmaic_secret_key) を参照してください。

データベースを共有する**複数のインスタンス**には、共有された永続的なデータディレクトリも 1 つ必要です（作業ディレクトリの `data/`、イメージでは `/app/data`。たとえば各インスタンスに同じボリュームやネットワークファイルシステムをマウントします）。授業ドキュメントと生成された授業メディアは PostgreSQL（`ASSET_S3_BUCKET` を設定した場合は S3）に保存されますが、次のファイルは各プロセスのデータディレクトリに置かれます：アップロードされた資料ファイルとその抽出結果、エージェントが編集する授業のナレーションと資料メディア（`data/classrooms`、または `OPENMAIC_CLASSROOMS_DIR`）、利用記録（`data/usage`）、自動生成されたインスタンスシークレット。別のインスタンスが引き継いだ生成は、アップロードされた資料をここから読み込みます。

## 生成の実行

すべてのサーバープロセスで生成ワーカーが動作し、`OPENMAIC_AGENT_RUNTIME_ENABLED` には依存しません。次の変数で調整できます（値は正の整数）。

| 変数 | デフォルト | 意味 |
| --- | --- | --- |
| `OPENMAIC_MAX_ACTIVE_RUNS_PER_OWNER` | `2` | 1 人のオーナーが同時に進行できる生成の数。アウトラインの確認待ちや、失敗したステップで一時停止している生成は数えません。上限を超えると、開始・アウトラインの確認・リトライは `429 ACTIVE_RUN_LIMIT` を返します。 |
| `OPENMAIC_MAX_WAITING_RUNS_PER_OWNER` | `10` | 1 人のオーナーが同時にアウトラインの確認待ちにできる生成の数。 |
| `OPENMAIC_GENERATION_RUN_MAX_CONCURRENT` | `4` | 1 つのプロセスが同時に実行する生成の数。 |
| `OPENMAIC_GENERATION_RUN_STREAMS_PER_OWNER` | `16` | 1 人のオーナーが 1 つのプロセスで同時に開ける生成イベントストリームの数。 |
| `OPENMAIC_GENERATION_RUN_RETENTION_HOURS` | `24` | 終了した生成が完全なイベントログを保持する時間（時間単位）。その後は圧縮されます。 |

生成はエージェントランタイムのリース設定（`OPENMAIC_AGENT_RUNTIME_SCAN_INTERVAL_MS`、`_HEARTBEAT_MS`、`_LEASE_TTL_MS`、`_MAX_ATTEMPTS`。`.env.example` を参照）を共有します。サーバーを停止すると実行中の生成は退避され、別のインスタンスか、再起動した同じインスタンスが続きを実行します。

## サーバー側永続化（PostgreSQL）

OpenMAIC は授業、チャット履歴、学習の進捗、生成メディアを PostgreSQL に保存するため、**`DATABASE_URL` は必須**です。未設定の場合、サーバーは `[boot] Invalid server configuration; the server will not start: DATABASE_URL is not set. ...` と対処方法を出力し、終了コード `1` で終了します。永続化用の HTTP API は OpenMAIC に組み込まれており、追加の永続化サービスは不要です。

`docker compose up` はアプリの横で PostgreSQL を起動し、`DATABASE_URL` を設定します。ローカル開発では、`pnpm db:up` が同じサービス定義から独立した開発用データベース（専用の Compose プロジェクトとボリューム `openmaic-dev-db`。このマシン上のすべてのチェックアウトで共有。スタックのデータベースには影響しません）を `127.0.0.1`（ポート `OPENMAIC_DB_PORT`、既定 `5432`）で起動し、`pnpm db:down` で停止します。その後 `.env.local` に接続情報を設定します：

```bash
DATABASE_URL=postgres://openmaic:openmaic-dev@127.0.0.1:5432/openmaic
```

永続化専用の認証情報はありません。各リクエストはオーナー解決で得られたオーナー（既定ではブラウザごとの匿名 Cookie）に帰属し、ランタイムセッションとメディアはそのオーナーごとに分離されます。既定の識別はブラウザを分離するだけで誰も認証しないため、実ユーザー向けのデプロイでは自前のアカウントに基づくオーナー認証メソッドを登録してください。以前のリリースの `PERSISTENCE_DEV_TOKEN` / `NEXT_PUBLIC_PERSISTENCE_TOKEN` は削除され無視されます。旧来のブラウザ生成の学習者キーで保存されたランタイムセッションにはアクセスできなくなります。`PERSISTENCE_DEV_TOKEN` が唯一のアクセス制御だった場合は、アップグレード前に `ACCESS_CODE` やゲートウェイで保護するか、オーナー認証メソッドを登録してください。

PostgreSQL のデータは `openmaic-postgres` ボリュームに保存されます。`PERSISTENCE_POSTGRES_PASSWORD` はデータベースディレクトリ初回初期化時にのみパスワードを設定し、その後の環境変数変更では既存ユーザーのパスワードは自動的に変更されません。

`OPENMAIC_SECRET_KEY` を設定していない場合、`openmaic-data` ボリュームには `instance-secret.key` も保存されます。これは自動生成されたインスタンスシークレットで、モデル設定に保存されたプロバイダーのキーを暗号化します。データベースと一緒にバックアップしてください。これがないと、保存済みのキーを再入力する必要があります。

以前のリリースでは授業をブラウザ（IndexedDB）に保存できました。このモードは廃止され、`NEXT_PUBLIC_PERSISTENCE` ビルド変数は無視されます。その方法でブラウザに保存された授業は、そのブラウザでアップグレード後のアプリを初めて開いたときに自動的にサーバーへ移されます。一方向のインポーターが、それらを（チャット、学習の進捗、フォルダー、メディアとともに）サーバーがそのブラウザについて解決した所有者にコピーし、ブラウザ内の元のデータには手を加えません。インポートはブラウザごとに一度だけです。サーバーはそのブラウザを、アップグレード後のアプリを最初に読み込んだ所有者に紐付け、統合（サインイン時に匿名の所有者がアカウントに統合されること）によって紐付けはアカウントに移ります。サーバーはそれ以外の所有者のためのインポーターの要求を拒否します。それ以外に同じブラウザを後から使う所有者には何もインポートされません。操作は不要で、UI も表示されません。問題があればブラウザのコンソールに `[legacy-browser-import]` という接頭辞で記録されます。

## 1.1.x からのアップグレード

| デプロイ | 手順 |
| --- | --- |
| `docker compose` | 新しいリリースを取得し、`docker compose up --build` を実行します。モデル設定を `openmaic.yml` または **設定 → モデル** に移し（`openmaic.yml` がない間はプロバイダーの環境変数も引き続き使えます）、`MODEL_ROUTES` をスロットとして書き直してください。`openmaic.yml` なしで `MODEL_ROUTES` を設定したサーバーは起動を拒否します。ローカルに授業があるブラウザでは、インポートのためにアプリを一度開いてください。 `.env.local` で `PERSISTENCE_SHARED_OWNER_ID` を設定している場合は、`OWNER_SINGLE_USER=false` も設定してください（Compose はシングルユーザーモードで起動するようになりました）。以前のサーバー側デプロイで匿名オーナーが持っていた授業は、シングルユーザーに自動では統合されません。それらを作成した各ブラウザから `POST /api/identity/claim` で引き継いでください（ブラウザを開いてインポートされるのは、そのブラウザがローカルに保存していたデータだけです）。 |
| `pnpm start` と自前の PostgreSQL | `DATABASE_URL` と ID モードを設定し、複数インスタンスでデータベースを共有する場合は `OPENMAIC_SECRET_KEY` も設定します。あとは上と同じです。 |
| Vercel | 1.1.x にとどまるか、同じデータベースを使う常駐ホストに移行します（下記）。 |
| Skill / API | 更新された `openmaic` skill に従い、同じオーナーとして資料をアップロード、送信、ポーリングします。 |

ブラウザのデータ（授業、モデル設定、カスタムエージェント）は、各ブラウザがアップグレード後のアプリを初めて開いたときに一度だけインポートされます。モデル設定の移行は[設定](./configuration.mdx#旧設定からの移行)を、破壊的変更の一覧は [CHANGELOG](https://github.com/THU-MAIC/OpenMAIC/blob/main/CHANGELOG.md) を参照してください。

## Vercel（1.1.x まで）

サーバーレスでのデプロイは OpenMAIC 1.1.x までサポートされ、[リポジトリの README](https://github.com/THU-MAIC/OpenMAIC#vercel-deployment-up-to-11x) の Deploy ボタンは `release/1.1.x` ブランチをデプロイします。このようなデプロイは、後でデータを失わずに常駐ホストへ移行できます。新しいホストの `DATABASE_URL` を（使っていた場合は）元のデータベースに向け、同じアドレスで公開してください。ブラウザはサイトごとにデータを保存しており、訪問者のブラウザにある授業は、各ブラウザがアップグレード後のアプリを初めて開いたときにインポートされます。

## オプション：MP4 動画エクスポート

「動画エクスポート」機能は、まずブラウザで自己完結型の Hyperframes プロジェクトを生成し、独立した `render-service` が Chromium と FFmpeg を使って MP4 にレンダリングします。このサービスは任意であり、通常の授業生成には影響しません。

`video-export` プロファイルを有効にします：

```bash
docker compose --profile video-export up --build
```

Compose は `RENDER_SERVICE_URL` を通じて OpenMAIC とレンダリングサービスを接続します。このプロファイルを有効にしないか、レンダリングサービスが利用できない場合は、エクスポートはプロジェクト ZIP のダウンロードにフォールバックし、ローカル CLI でのレンダリングを想定します。レンダリングサービスは分離されたネットワークで動作し、起動時に `NET_ADMIN` 権限が必要です。詳細や独立デプロイ方法はリポジトリの [`render-service/README.md`](https://github.com/THU-MAIC/OpenMAIC/blob/main/render-service/README.md) を参照してください。
