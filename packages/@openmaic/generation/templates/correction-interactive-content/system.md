# Source-bound correction hand-simulation widget

Generate one compact, complete HTML5 document for the supplied source-bound correction lesson. Use the existing native HTML renderer. This is an interactive hand simulation, not a compiler, interpreter, submission run or judge result. Follow the supplied teaching language; keep its programming-language metadata separate.

## Compact native HTML contract

- Output only a complete document ending in `</html>`. Keep JSON, CSS and JavaScript concise; no decorative duplication, frameworks, external assets, network calls, dynamic code evaluation or copied libraries.
- Use accessible DOM text/code/state tables and simple responsive CSS. Do not generate a canvas, physics animation, `requestAnimationFrame`, autoplay or start/pause/restart machinery. The lesson is controlled by explicit next, back and reset buttons.
- Provide legal, editable inputs appropriate to the actual source (not necessarily numeric sliders). Apply exact inclusive/exclusive bounds and input format. Label exposed inputs with their actual variable names using `data-var`; include only evidence-supported presets, if useful. Do not assume any particular variables, values or program.
- Define one source-grounded input specification and use it for both DOM input attributes and JavaScript validation. Keep the required format and inclusive/exclusive bounds consistent; when an attribute cannot express a bound exactly, enforce it explicitly without advertising a contradictory range.
- Validate each complete raw input for presence and the source-required format before conversion; do not use `parseInt`, prefix parsing or coercion to accept a truncated decimal or trailing text as an integer. For numeric input, strictly convert the validated full value, then require a finite number and, where the specification requires it, an integer before bounds checks or arithmetic. The displayed accepted input and the value used in the calculation must agree.
- Show the initial state, current step/progress, and the relevant original/reference hand-calculation state. Each displayed step must follow the implemented source-grounded transitions. A separate HTML/JS calculation must not be presented as actual source-language execution.
- At the labelled source position, a current variable may show only a value established by operations already performed in that trace or by the actual source language's initialization rules. If neither has established a value yet, omit the variable or explicitly mark it as not yet assigned in the teaching language until a value is established. Do not evaluate its future expression or fill in zero merely to populate a table. A legitimate zero value is different from an unassigned variable. Back and reset restore assignment status as well as values.
- For current-variable state tables, use a simple two-column layout: variable name and current value, with teaching-language headers. Build both cells of each body row from the same variable/state entry; use exactly two header cells and two cells per body row, without colspan/rowspan in these tables. Do not separately prepend a row-label column or a variable-header list that has no matching body cells. Keep original and reference state entries separate.
- Render each step from one coherent current state: variable cards, calculation notes, progress and expression labels must describe that same step. Next, back, reset and input changes must update or roll back all of these together. When a variable is reassigned, its displayed expression and value must change together, including the final step.
- If future or final values are precomputed for comparison, show them separately and explicitly label them as a precomputed comparison. Do not put those values in the current-state display or imply that an unperformed step has already executed.
- Implement real `type="button"` controls `#step-next`, `#step-back` and `#step-reset`, with matching `data-role="next"`, `data-role="back"` and `data-role="reset"`, visible teaching-language labels and keyboard/focus support. Expose the current status at `#step-status` (`data-role="status"`) and progress at `#step-progress` (`data-role="progress"`). These are DOM conventions, not a new server message format.
- There is no autoplay control. At the initial step, back is disabled. At the final step, next is disabled and the status is completed immediately, without an extra click. Going back restores the preceding state, immediately leaves completed status, and updates all labels/disabled states. Reset restores the initial step for the currently selected inputs and updates every state/display/control. Changing inputs validates them, rebuilds the trace and resets progress atomically. Do not retain stale cached results or button text.
- Treat invalid input as one coherent unavailable state: update the internal step, all state tables, expressions, precomputed comparisons, overall/local status, progress and navigation controls together. Clear or explicitly mark calculated displays as unavailable, disable next/back, and keep reset consistent with that invalid state; do not reset only the step while retaining old UI. When inputs become valid again, rebuild all state and displays consistently from the initial step.
- Fit the existing iframe with responsive readable content and usable touch targets. Inputs, state tables and controls must remain usable on narrow screens. Do not drop source facts or a necessary repair to make the document shorter.

- `SET_WIDGET_STATE`: apply the supplied variable keys in `state` to their actual exposed inputs (`data-var` or existing input IDs), through the same validation/state-update path as user edits; rebuild the state/trace and reset progress consistently.
- `HIGHLIGHT_ELEMENT`: select `target` with `document.querySelector` and visibly highlight the real element, with cleanup.
- `ANNOTATE_ELEMENT`: show `content` as text near the actual `target`, with cleanup; never interpret annotation text as HTML or code.
- `REVEAL_ELEMENT`: reveal the actual element selected by `target`.

Embed `<script type="application/json" id="widget-config">` containing a JSON object with `type: "simulation"`, an evidence-based concept/description, `exposedVariables: string[]` listing the exact declared input keys, and any presets that actually exist in this document. Use `exposedVariables: []` when there are no exposed inputs; this permits no `SET_WIDGET_STATE` assignments. Configuration, controls, implemented transitions and visible state must agree. Do not add `teacherActions`; native actions are generated separately from this actual HTML/JavaScript, configuration and real element inventory. A valid HTML response is not proof of factual correctness or a working widget; the final material still undergoes the existing review.
